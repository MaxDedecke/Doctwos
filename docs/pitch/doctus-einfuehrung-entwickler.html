Doctus

Fragen an gewachsenen Code stellen und Antworten bekommen, die man nachprüfen kann.

Eine Einführung für das Team hinter SecDocs und DSEngine.

Ein ganz normaler Dienstag

Neue Archivzeitstempel sollen mit SHA-512 statt SHA-256 entstehen. Bevor du die erste Zeile änderst, willst du wissen:

  • Wo wird der Algorithmus gewählt, und wo steht er fest im Code?
  • Welche Teile von SecDocs und DSEngine hängen daran?
  • Was passiert mit bestehenden Evidence Records?
  • Gab es das Thema schon einmal als Issue?

Und so sieht die Suche heute aus:

  • IDE. Kennt nur die Module, die gerade offen sind.
  • GitLab-Suche. Findet Zeichenketten, aber keine Aufrufketten.
  • Confluence. Die Seite gibt es. Ob sie noch stimmt, weiß niemand.
  • Issues. Irgendwo, unter einem anderen Begriff.
  • Die Kollegin, die es weiß. Diese Woche im Urlaub.

Das Wissen ist schon da. Es liegt nur verteilt.

Wissensmanagement heißt hier nicht, noch ein Wiki zu pflegen. Es heißt, das vorhandene Wissen aus Code, Wikiseiten und Tickets an einer Stelle auffindbar zu machen, die Zusammenhänge zwischen ihnen sichtbar zu machen und jede Antwort auf ihre Quelle zurückzuführen.

Genau das macht Doctus.

Drei Sichten auf dieselben Dateien

Original

Die Datei so, wie sie in Git liegt. Sie bleibt immer die maßgebliche Quelle.

Struktur

Was der Parser daraus erkennt: Klassen, Methoden und wer wen aufruft.

ArchiveEndpoint.archive
  ruft EvidenceService.renew
  ruft TimestampClient.request

Bedeutung

Textabschnitte als Zahlenvektoren. Damit findet die Frage „Beweisdaten erneuern“ diese Methode.

[0.031, -0.118, 0.274, …]
1.024 Werte je Abschnitt

Alle drei Sichten hängen am selben Anker: Datei und Zeile

Was mit einer Quelle passiert

  1. Anbinden

    Ein GitLab-Repository, ein Confluence-Bereich, GitLab Issues oder ein Ordner wird einem Projekt zugeordnet.

  2. Synchronisieren

    Ein Hintergrund-Job holt die Inhalte. Bei Abbruch setzt er dort wieder auf, wo er war.

  3. Parsen

    Code wird in Objekte und Beziehungen zerlegt, Dokumente in Abschnitte.

  4. Einbetten

    Ein lokales Modell rechnet jeden Abschnitt in einen Vektor um.

  5. Speichern

    Alles landet in PostgreSQL. Die Vektorsuche übernimmt pgvector.

Das läuft wie eine Pipeline in Celery-Workern, nie im Web-Request. Ausgelegt ist es auf Bestände bis 100 GB. Den Fortschritt zeigt das Job-Center.

Der Parser rät nicht

@WebService(serviceName = "ArchiveService")
public class ArchiveEndpoint {

  @Inject
  EvidenceService evidence;

  @WebMethod
  public EvidenceRecord getEvidence(String aoid) {
    return evidence.forArchiveObject(aoid);
  }
}
  • INJECTSEvidenceService in ArchiveEndpoint
  • EXPOSESSOAP-Operation getEvidence auf ArchiveEndpoint.getEvidence
  • CALLSArchiveEndpoint.getEvidence auf EvidenceService.forArchiveObject

Das Parsen ist deterministisch und kommt ohne KI aus. Maven-Module, Parents, BOMs und Scopes werden statisch aus den POMs gelesen. Doctus führt beim Import weder Maven noch Plugins aus.

Der Parser kennt Spring, CDI, JAX-RS und JAX-WS samt WSDL und XSD. Was sich nicht eindeutig auflösen lässt, bleibt als offen markiert.

Suchen nach Bedeutung statt nach Zeichenketten

Wie wird ein Beweisdatensatz erneuert?
  • Java-CodeHashTreeRenewal.execute()
  • ConfluenceÜbersignatur nach Algorithmenwechsel
  • GitLab IssueERS-Erneuerung bricht bei großen Hashbäumen ab

Keiner der drei Treffer enthält das Wort „Beweisdatensatz“. Ein Embedding-Modell bildet jeden Textabschnitt auf 1.024 Zahlen ab. Abschnitte mit ähnlicher Bedeutung liegen dabei nahe beieinander, auch über Sprachen und Schreibweisen hinweg. Doctus kombiniert diese Suche mit der klassischen Volltextsuche und mit der Struktur aus dem Parser.

Wie eine Antwort entsteht

Frage

In normaler Sprache, im Kontext eines Projekts.

→

Belegpaket

  • passende Code-Ausschnitte
  • Aufrufer und Abhängigkeiten
  • Wikiseiten und Issues
  • jeweils mit Datei und Zeile
→

Antwort

Ein Sprachmodell formuliert sie aus dem Paket, mit klickbaren Quellen.

Das Sprachmodell kennt euren Code nicht. Es liest bei jeder Frage nur das Belegpaket, das Doctus vorher zusammengestellt hat.

Der Fachbegriff dafür ist Retrieval-Augmented Generation. Der wertvolle Teil ist das Zusammenstellen des Pakets. Das Formulieren ist der kleinere Schritt.

Jede Aussage zeigt auf ihre Stelle

Wo wird der Hashalgorithmus für neue Zeitstempel festgelegt?

Der Standardwert steht in CryptoPolicy.defaultDigest CryptoPolicy.java:41 und ist dort auf SHA-256 gesetzt.

Gelesen wird er von TimestampClient.request TimestampClient.java:88, also bei jeder Zeitstempelanfrage aus EvidenceService.renew.

In der DSEngine habe ich keine Stelle gefunden, die diesen Wert liest. Ob sie einen eigenen Standard verwendet, lässt sich aus dem Index nicht belegen.

Ein Klick auf eine Quelle öffnet die Datei an genau dieser Zeile. Was sich nicht belegen lässt, nennt die Antwort ausdrücklich als Lücke, statt es zu ergänzen.

Der Arbeitsraum

Bis zu vier Ansichten nebeneinander. Wer ein Objekt in den Fokus nimmt, sieht es in allen offenen Ansichten zugleich.

Chat

Fragen stellen, Quellen anklicken, Code als Kontext anheften.

Code-Editor

Die Originaldatei mit Sprung zu Definitionen und Aufrufern.

Web-Ansicht

Wikiseiten und Issues im gewohnten Format, mit dem dort genannten Code verlinkt.

Abhängigkeiten

Wer ruft wen, über bis zu fünf Ebenen und alle Repositories.

Wissensgraph

Code, Dokumente und Themen als ein Netz, gruppiert nach Kopplung.

Link-Manager

Verbindungen zwischen Code und Dokumentation gezielt prüfen und pflegen.

Erkenntnisse: Wissen, das nirgends steht

Wird ein Hashalgorithmus schwach, reicht eine neue Zeitstempelkette nicht. Dann plant der RenewalPlanner eine Hashbaum-Erneuerung ein.
RenewalPlanner.java:58 Erneuerungsstrategie.adoc:12

Die Regel steht in der Norm. Wie sie in eurem Code umgesetzt ist, weiß oft nur eine Person. In Doctus wird daraus eine Erkenntnis mit Belegen im Code und in Dokumenten.

  1. 1

    Entwurf

    Jemand schreibt die Aussage auf und hängt Belege an.

  2. 2

    Prüfung

    Eine zweite Person gibt frei. Das Vier-Augen-Prinzip wie beim Merge Request.

  3. 3

    Gebunden

    Die Freigabe gilt für genau den Commit, an dem die Belege geprüft wurden.

  4. 4

    Veraltet

    Ändert sich der Code an einer Belegstelle, geht die Erkenntnis zurück in die Prüfung.

Nur freigegebene und aktuelle Erkenntnisse fließen in Chat-Antworten ein.

Beweiswert, auf Code angewendet

Das Prinzip kennt ihr aus eurer eigenen Arbeit. Doctus wendet es auf Wissen über Software an.

BeweiswerterhaltungDoctus
Ein Dokument ist so viel wert wie sein Nachweis.Eine Antwort ist so viel wert wie ihr Beleg.
Der Evidence Record bindet einen Hashwert an einen Zeitpunkt.Eine Erkenntnis bindet ihre Belege an einen Commit.
Wird ein Algorithmus schwach, wird erneuert.Ändert sich der belegte Code, wird erneut geprüft.
Die Prüfung gelingt auch ohne den Hersteller.Jede Quelle lässt sich im Original nachlesen.

Das Änderungspaket: Was berührt mein Commit?

  • Betroffene MethodenJede geänderte Zeile wird der Methode zugeordnet, in der sie steht.
  • Aufrufer und EndpunkteWer diese Methoden nutzt, bis hin zu REST- und SOAP-Schnittstellen.
  • ErkenntnisseWelche festgehaltenen Aussagen sich auf genau diese Stellen stützen.
  • Maven- und TestergebnisseAus der Pipeline, fest an diesen Commit gebunden.

Die Ergebnisse kommen aus eurem eigenen Build. Ein kleines Skript im CI-Job startet mvn clean verify und meldet das Ergebnis mit einem Token, das an eine Quelle gebunden ist.

maven-verify:
  stage: test
  script:
    - python3 "$DOCTUS_CI_RUNNER"
        --variant jdk21-default
        --java-version 21

Beispiele für GitLab CI und GitHub Actions liegen bei. Doctus selbst startet nie einen Build.

Auch Coding-Agenten fragen Doctus

Agenten in der IDE oder im Terminal sprechen Doctus über das Model Context Protocol an. Das ist eine offene Schnittstelle, über die ein Agent Werkzeuge aufrufen kann.

Der Aufruf answer_context liefert dasselbe Belegpaket wie im Chat. Ziel ist eine Frage mit einem einzigen Aufruf.

Der Agent muss sich nichts aus zehn Dateisuchen zusammensuchen.

Unsere Messungen zeigen: Wenn das Paket die Antwort schon enthält, bestehen auch kleine lokale Modelle die Prüfaufgaben zuverlässig.

Was Doctus nicht ist

  • Kein Ersatz für Review und Tests

    Doctus verkürzt den Weg zu den richtigen Stellen. Die Entscheidung trefft weiterhin ihr.

  • Kein weiteres Wiki

    Es liest, was in GitLab und Confluence schon steht. Gepflegt wird dort, wo ihr ohnehin arbeitet.

  • Kein Code-Generator

    Doctus erklärt und belegt bestehenden Code. Es schreibt keinen.

  • Kein Orakel

    Ohne Beleg keine Behauptung. Eine Antwort ohne Quelle ist ein Fehler, den wir hören wollen.

Die wichtigsten Begriffe

Wissensquelle
Ein angebundenes System: Git-Repository, Confluence, Jira, GitLab Issues oder ein Ordner.
Projekt
Zusammengehörige Quellen mit eigenen Mitgliedern und Rechten.
Objekt und Beziehung
Was der Parser erkennt, etwa eine Methode und ihre Aufrufe. Immer mit Datei und Zeile.
Embedding
Ein Textabschnitt als Zahlenvektor, damit Suche nach Bedeutung möglich wird.
Belegpaket
Das, was Doctus zu einer Frage aus dem Index zusammenstellt. Chat und Agenten lesen nur das.
Erkenntnis
Festgehaltenes Wissen mit Belegen und Vier-Augen-Freigabe, gebunden an einen Commit.
Änderungspaket
Alles, was ein Commit berührt, mit Erkenntnissen und CI-Ergebnissen.
MCP
Die Schnittstelle, über die Coding-Agenten Doctus als Werkzeug nutzen.

  • Stellt sie in Doctus.
  • Klickt auf die Quellen und prüft, ob die Antwort stimmt.
